# 真机端到端测试：代理 / 奖励 / 支付

## 目标
在一号机 `sub2api-custom`（:18080，镜像 `custom-latest` = 34ef3fc05）上，用真实 HTTP 接口
+ 模拟易支付网关 + 必要时直接写库，把定制的两级代理分润、普通邀请奖励、被邀请人首充奖励、
充值 / 消费两种返利基数、支付下单 / 回调 / 退款完整跑一遍，逐条核对流水金额。

## 测试环境
- 目标：`http://216.75.75.82:18080`，库 `sub2api-custom-postgres`。测试前备份：
  `/root/sub2api-custom-backups/pre-e2e-20261022-113129.dump`。
- 支付：容器 `sub2api-e2e-easypay-mock`（python:3.13-alpine，挂在 sub2api-custom 网络），
  实现 `mapi.php` 下单、`api.php?act=order` 查单、`api.php?act=refund` 退款；
  控制端点 `/_pay` 按易支付规则 MD5 签名后回调 `/api/v1/payment/webhook/easypay`。
  后台新建易支付实例「e2e-mock」指向它，原实例「dulu」测试期间停用，结束后恢复。
- 账号：测试账号均为 `e2e-*@e2e.test`；临时管理员 `e2e-admin@e2e.test`（合规确认沿用站长已签记录），结束后删除。
- 设置：测试前快照所有 affiliate / payment / recharge 设置，结束后逐键恢复。
- 驱动：`/tmp/e2e/run.py`（本地 Python，requests + ssh psql），每条用例记录「预期 / 实际 / 结论」。

## 基线设置（除用例另行说明）
利润池 P=30%，二级 R2=20%，专属比例关；普通邀请 percent 5%；被邀请人奖励关；冻结 0；
有效期 0；单人上限 0；返利基数 recharge；升级 manual；任命开、上限 0；管理员充值返利关。

## 用例

### CFG 配置
| ID | 场景 | 预期 |
|---|---|---|
| CFG-01 | 管理端 PUT 基线设置 | 成功，库中值一致 |
| CFG-02 | 设 R2 > P（P=10, R2=20） | 拒绝或 R2 被收敛到 ≤ P，不出现 R2 > P |

### REL 绑定与归属快照（注册带 aff_code）
链 1：`B(一级) → A(B 任命为二级) → U1(普通) → U2(普通)`
| ID | 场景 | 预期 |
|---|---|---|
| REL-01 | A 用 B 的码注册 | inviter=B, owner=B, owner_level=1, upline=NULL, inviter_was_agent=true |
| REL-02 | B 任命 A 为二级（用户端接口） | A.level=2, source=agent, updated_by=B |
| REL-03 | U1 用 A 的码注册 | owner=A, level=2, upline=B, inviter_was_agent=true |
| REL-04 | U2 用 U1 的码注册（U1 普通） | owner=A, level=2, upline=B, inviter_was_agent=false |
| REL-05 | 管理端邀请记录 | inviter_level / invitee_level 为当前等级 |

### CON 消费基数（定时结算，写 usage_logs）
链 3：`CB(一级) → CA(二级) → CU1(普通) → CU2(普通)`
| ID | 场景 | 预期 |
|---|---|---|
| CON-01 | 消费基数下 CU2 支付充值 50 | 充值时不产生代理 / 比例奖励 |
| CON-02 | CU2 余额消费 30 + 订阅消费 10，等待结算 | CA 6、CB 3、CU1 1.5，base=30，source_usage_until 有值 |
| CON-03 | CU2 再消费 40 | 按剩余真实充值 20 结算：CA 4、CB 2、CU1 1 |
| CON-04 | CU2 再消费 10 | 已到封顶，无流水，水位推进 |
| CON-05 | CU1 充 100、退 60，消费 50 | 按 40 结算：CA 8、CB 4，无比例奖励 |
| CON-06 | Z2 绑定前消费 20，管理员补绑到 CA 后消费 10（已充 100） | 只结算绑定后的 10 |
