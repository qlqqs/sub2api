# 技术设计（最终评审稿）

## 边界

配置集中入口复用现有 API/service/字段，必要时增加仅成本字段的读写适配以避免前端整对象覆盖。禁止建第二份业务配置。新的持久化只用于重算任务、快照、审计和任务失败续跑。

## UI 与配置写入

FinanceSettingsTab 拆分四个内部区块；账号列表 → BaseDialog。直接复用 AccountModelCostEditor、FinanceExpenseDialog、PricingEntryCard 和 common 组件；从 ChannelsView 最小提取成本规则编辑/序列化给两处共用，原渠道表单行为用回归测试保护。渠道规则不得丢失平台、模型、顺序、匹配账号/分组及高级字段。

默认倍率、模型倍率、固定成本和渠道规则属于不同资源；各分区明确保存状态，不假装跨 API 原子提交。若需共用保存动作必须显示每项结果和可重试项。共享规则使用版本/内容摘要并发校验，冲突返回最新配置与重载指引，不能覆盖其他管理员改动。

## 历史计算

- 以记录保留的用量、实际上游模型、服务等级、实际思考等级、图片张数和发生时间作为输入，使用当前成本配置；不重算客户端 total_cost/actual_cost。
- 提取/共用成本规则解析纯函数，在线请求保持原行为；重算增加严格的历史依据校验，不能调用在线默认 1 张、静默 fallback 的入口。
- 固化相关账号/渠道/分组成本规则和模型文件版本/内容；复算不重新读取漂移中的在线缓存。只保存成本相关白名单字段，不保存 credentials、密钥或请求正文。
- 旧值/新值及报表汇总用 decimal，沿用数据库快照精度与既有单位转换；预览和执行共享同一量化结果。
- 支付任务仅按订单已保存实例关系修正 channel_fee_rate；NULL 与 0 分开保存。现金收入确认受此变化，但用户余额与已付金额不变。

## 数据与接口草案

新增前向迁移（实施时取下一可用编号），原生 SQL 仓储：

1. `finance_recalculation_batches`：类型、过滤范围、操作者、当前状态、配置摘要/白名单快照、数据截止水位、计数/总差额、租约/心跳、幂等键、错误、时间。
2. `finance_recalculation_items`：批次、稳定目标标识（usage id+created_at，兼容分区）、旧/新成本字段或订单费率（保留 NULL）、输入指纹、原因、应用状态。不得因原记录清理而级联删除审计。
不引入专用于撤销归属/ABA 冲突的目标版本链或反向批次关联；执行仍使用行锁、输入指纹、原值比较和任务状态防止陈旧预览覆盖及重复应用。

`/admin/finance/recalculations`：创建预览、分页列表/详情/条目、确认执行、重试同步；不提供 undo/undo-preview 接口。接口使用明确状态/错误码，例如 preview_expired、source_changed、rule_changed、sync_failed。服务端验证管理员身份、预览归属/有效期、数量与日期上限。

预览后台扫描并分页落条目，不将百万记录放在请求内存；冻结截止时间/ID，后续新增记录不混入已确认批次。默认先限制批量大小并引导分段，具体阈值由本机压测确定，不改变显式预览/确认契约。

## 执行、并发与恢复

状态：previewing → ready → queued → applying → syncing → completed；另有 expired/conflict/failed，失败保留阶段与已应用数。DB 持久任务由 worker claim/租约推进，关闭浏览器不取消；重启从安全边界恢复。

每个写批次事务内：按稳定顺序锁行，核对目标/输入指纹/旧成本值与配置版本，保存原值后更新成本字段及条目状态。使用唯一约束和条件状态转换防双重执行。预览整体失效必须在开始前拒绝；执行中外部改动则停止未应用部分、显示真实部分状态，不覆盖冲突行。已经应用的部分保留并可审计；未完成部分安全续跑，冲突部分需重新预览为新批次，不提供撤销。

确认弹窗明确不可撤销；保留原值用于审计，不作为自动恢复接口。数据库事务提交前失败仍正常 rollback；这与对已提交批次提供业务撤销是两回事。

## 统计一致性（重点验证）

- 账号与财务明细按现有公式读取新快照；固定成本仍只是财务排除规则，其他统计不强行清零。
- 小时/日聚合以受影响桶为单位修正 account_cost，优先使用同事务成本净差额而非删除整桶；保留收入、请求数、活跃用户等不相关字段。缺桶时先判断是否有完整明细可安全重建，否则报待处理，禁止用不完整历史覆盖旧汇总。
- 写批次与定时聚合/补算/清理使用一致锁协议与顺序，防旧快照聚合覆盖新成本；实施先用并发集成测试证明方案，再接入 worker。不能只给重算加单边锁而聚合方不参与。
- 审计和明细写入原子；聚合/缓存阶段可恢复且具幂等标识，不重复累加差额。所有阶段完成才标 completed。
- dashboard 缓存增加修正代际/读写栅栏，防在途旧查询写回；缓存刷新失败保留 syncing 可重试。账号前端缓存和财务页失效/刷新随任务状态处理。
- 分组/用户日汇总触发器可能因 UPDATE 被触发；验证数值不漂移，避免不必要全表重建。

## 兼容、上线与回滚

不改已执行迁移，新表不自动触发任何重算；旧入口继续可用。只在本机新建数据与 mock 上游验证。应用回滚不删除审计表；产品不提供历史数据撤销。误配置通过新的显式重算批次纠正；灾难恢复只能另行评估并获用户授权使用备份（需考虑备份之后的新增业务数据），不能通过回滚代码假装撤销数据。

## 实施前技术验证项

并发锁/缓存栅栏、保留期边界、支付退款期间的指纹、分区目标键、在线/离线计算一致性必须有测试证据；失败时不降低安全契约。暂不承诺大数据性能数值，压测后设保守批量上限。若发现须改变产品范围或只实现部分规则，回到用户评审，不静默缩范围。


## 2026-10-26 用户批准：现存明细首次基线

以现有任务 filter JSON 的 accept_retained_baseline（默认 false，仅 usage_cost）记录显式选择，config_snapshot 保存类型化 retained_baseline（版本、时区、逐日来源数/摘要及原小时/日桶）。复用既有预览确认和审计事务，不新增全局水位或变更已应用迁移。最大31日及2000条整日明细；账号/模型筛选也必须核对完整日期。Apply 使用配置表→usage_logs SHARE→聚合 advisory 的锁序，锁内重新对账/指纹校验，事务内更新成本和汇总。一次性基线不是历史无删除的证明。数据库备份为上线执行前操作步骤，本轮不执行线上写入。


## 2026-10-26 执行前提收敛：停流量重算

用户明确：重算会在停止所有请求的情况下进行，不会有新增记录，要求避免复杂化。

正式操作流程仅为：停止请求入口并等待在途请求结束 → 数据库备份 → 现存明细预览/确认重算 → 核对财务、账号、看板 → 恢复请求。停流量由操作人员完成；本页面不会自行停服务或创建备份。

不支持/不再扩展在线并发重算算法、自动停流量编排、全库历史补证或撤销。保留已实现的整日对账、旧值审计和单事务原子执行；锁只是误操作防护。恢复请求后的正常汇总不能被旧日期标记冻结，因此保留已验证的小范围标记版本修复（前向迁移260；不改257/258或其他任务的259）。

此授权仍不包含提交、推送、部署或修改一号机账目。
