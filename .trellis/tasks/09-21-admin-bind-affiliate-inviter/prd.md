# 管理员补绑邀请关系

## Goal

允许管理员为注册时未填写返利邀请码、当前尚未绑定邀请人的用户补录一次邀请关系，避免只能通过直接修改数据库处理，同时保持返利账务、邀请人数和审计记录一致。

## Background

- 注册接口中的 `invitation_code` 是注册准入兑换码；本任务处理的是返利邀请关系，即 `aff_code` 对应的 `user_affiliates.inviter_id`。
- 当前注册流程会初始化 `user_affiliates`，仅在注册请求携带 `aff_code` 时调用 `BindInviterByCode`（`backend/internal/service/auth_service.go:266-275`）。
- Repository 已通过事务和 `WHERE inviter_id IS NULL` 原子设置邀请人并增加邀请人的 `aff_count`（`backend/internal/repository/affiliate_repo.go:79-109`），但管理端没有补绑入口。
- 当前邀请记录使用 `user_affiliates.created_at` 作为“邀请时间”（`backend/internal/repository/affiliate_repo.go:386-433`）；对于注册后补绑，该时间不准确。
- 当前返利有效期以 affiliate profile 的 `created_at` 为起点（`backend/internal/service/affiliate_service.go:343-348`）；补绑用户需要改为以实际绑定时间为起点。

## Requirements

### R1. 管理员一次性补绑

- 管理员可以选择一个被邀请用户和一个邀请人，并提交补绑原因。
- 仅当被邀请用户从未绑定过邀请人时允许补绑。
- 补绑成功后不得通过该功能修改、替换或解除邀请人。
- 不允许用户邀请自己。
- 被邀请用户、邀请人必须是系统中可查询到的有效用户。
- 补绑是管理配置操作，不依赖邀请返利总开关当前是否启用；总开关关闭时仍不产生返利。

### R2. 并发和账务一致性

- 补绑必须在单个数据库事务中完成：写入邀请关系和绑定元数据，同时将邀请人的 `aff_count` 增加 1。
- 并发提交或重复提交时只能有一次成功，失败请求返回稳定的“已绑定”冲突错误。
- “曾经绑定过”由绑定时间标记判断；即使未来邀请人被软删除或外键行为使 `inviter_id` 为空，也不能再次补绑。
- 不修改、转移或重算已经存在的返利流水、冻结返利、可用返利或历史返利。

### R3. 返利生效边界

- 补绑不触发任何历史充值返利补算。
- 只有补绑成功后发生并进入现有返利入账流程的新充值/兑换/管理员充值，才按现有规则产生返利。
- 返利有效期从实际邀请关系绑定时间开始计算；历史注册时已绑定的记录保持与原行为等价。

### R4. 绑定元数据和记录展示

- 邀请关系记录实际绑定时间、绑定来源、操作管理员和补绑原因。
- 注册时自动绑定的来源记为 `registration`；管理员补绑来源记为 `admin`。
- 现有已绑定数据迁移时，以 affiliate profile 的 `created_at` 作为兼容绑定时间，并标记为 `registration`。
- 管理端邀请记录中的“邀请时间”使用实际绑定时间；API 字段可以继续保持 `created_at`，避免无必要的前端合约破坏。

### R5. 管理端 API 与审计

- 新增独立的管理员补绑端点，不把该行为混入邀请码/专属返利比例更新接口。
- 请求至少包含 `inviter_id` 和非空 `reason`；reason 去除首尾空白并限制为 1–500 个字符。
- 管理员身份从认证上下文读取，不接受客户端传入的操作者 ID。
- 该写操作进入现有管理端审计日志，使用稳定动作名 `admin.affiliate.inviter.bind`，审计中可追溯被邀请用户、邀请人、操作者、原因和成功/失败状态。

### R6. 管理端界面

- 在“邀请返利”管理区域提供“补绑邀请人”入口。
- 使用现有用户搜索能力分别选择被邀请用户和邀请人，不要求管理员手输数据库 ID。
- 表单显示选中的用户信息、必填原因，以及“绑定后不可修改、仅影响后续充值”的明确提示。
- 相同用户不能同时作为被邀请用户和邀请人；提交期间禁用重复提交。
- 成功后关闭弹窗、显示成功反馈并刷新相关邀请数据；失败时显示后端安全错误信息。
- 新增中英文 i18n 文案，并保证基本键盘操作和表单 label 可访问性。

## Acceptance Criteria

- [x] AC1：管理员为从未绑定邀请人的用户提交有效邀请人和原因后，API 成功返回；数据库写入邀请关系和绑定元数据，邀请人的 `aff_count` 恰好增加 1。
- [x] AC2：对已绑定或曾经绑定过的用户再次提交时返回 `409` 和稳定的 `AFFILIATE_ALREADY_BOUND` reason，原邀请关系和双方金额/计数不变。
- [x] AC3：邀请人与被邀请人相同时请求失败，且数据库无任何部分写入。
- [x] AC4：两个并发补绑请求最多一个成功，`aff_count` 不会重复增加。
- [x] AC5：补绑操作不会为绑定前已完成的充值创建返利流水；绑定后的新入账继续复用现有返利比例、冻结期、有效期和单用户上限规则。
- [x] AC6：返利有效期以绑定时间为起点；迁移前已经绑定的用户保持以原 `created_at` 近似起点的兼容行为。
- [x] AC7：邀请记录列表展示实际绑定时间，管理员补绑不会被错误显示成用户注册时间。
- [x] AC8：审计日志动作名为 `admin.affiliate.inviter.bind`，能够识别操作者、目标用户、邀请人、原因和请求结果。
- [x] AC9：后台界面可搜索并选择双方用户、填写原因和确认提交；自邀请、缺少原因和重复提交在 UI/后端边界得到处理。
- [x] AC10：后端单元/集成测试、前端 API/组件测试、类型检查及相关构建检查通过。

## Out of Scope

- 已绑定用户修改、解除或转移邀请人。
- 用户自行补填邀请码或自助申请改绑。
- 批量补绑或 CSV 导入。
- 历史订单返利补算、返利流水转移、冻结金额调整或已提现返利冲正。
- 修改注册准入用的 `invitation_code` 兑换码流程。
