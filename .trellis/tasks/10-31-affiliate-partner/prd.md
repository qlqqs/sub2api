# 合伙人：按区域利润分成

日期：2026-10-31。主代理负责规划和协调，实现交给子代理：后端 codex gpt-6-astra high，前端 claude opus-5.5 high，测试 codex gpt-6.1-sol high。技术设计见 `design.md`，接口见 `contract.md`，执行计划见 `implement.md`。

## 背景

- 现有两档代理，按客户的余额消费拿比例：渠道经理（一级）和分销代理（二级）。生产配置为利润池 11%、二级 7%，规则见 `docs/AGENT_PROFIT_SHARING_CN.md`。
- 新增合伙人，排在渠道经理之上：**合伙人 → 渠道经理 → 分销代理 → 客户**。
- 合伙人拿区域**真实利润**（收入 − 上游成本 − 代理分润）的 40%，不按消费额（流水）分。
- 用户 2026-10-29 提出过一条要求：合伙人在团队消费页能看到下面的所有信息。
- 现有两位合伙人，都是七号机上的现有账号（2026-10-31 查询）：

  | 账号 | 区域名 | 现状 |
  |---|---|---|
  | 75 号 `1185393366@qq.com`（malaixin） | 三科大 | 当天注册，已手动设为渠道经理，无上级、无团队 |
  | 62 号 `578486809@qq.com` | 重大 | 普通用户，无上级、无团队，余额 ¥1.83 |

  - 两人都没有存量客户，上线后不需要迁移数据。
  - 区域名由用户指定（2026-10-31），比例都是 40%。

## 已定决策（2026-10-31 与用户确认）

1. 公共支出（服务器、域名、支付开户等）不分摊给区域。只为某个区域花的支出，录入时指定该区域，从该区域利润里扣。
2. 固定成本账号：用户自己把它们折算成账号倍率成本，即移出财务页的固定成本列表并设置账号倍率。
   - 区域成本使用财务页同一套按请求成本。仍在固定成本列表里的账号，成本按 0 计。
   - 七号机已确认：低上游倍率优先和高级调度都没开，改倍率不影响选号。
3. 分成线下打款，系统只记录「已付」和备注。
4. 合伙人不能任命任何代理，代理都由后台任命。渠道经理任命分销代理的现有功能不变。
5. 合伙人能看到成本，但不出现供应商（账号名称或账号 ID）。成本按分组和按模型拆分（第二轮确认）。
6. 挂靠不设生效日期，挂上即永久，只往后算，挂靠之前的消费不算。
7. 后台把区域内的用户升为渠道经理时，自动挂到该区域的合伙人名下（第二轮确认）。
8. 设为合伙人、挂靠渠道经理都不能撤销，也不能改挂。操作前先预览，再二次确认（第二轮确认）。

## 需求

### 1. 合伙人

- 后台把现有用户设为合伙人，填写区域名（只作标签）和分成比例（默认 40%）。
  - 设为合伙人后，该账号内部按渠道经理档位处理，档位锁定，后台不能再改档位。这样客户绑定时，合伙人照常被记为归属代理。
  - 已经挂在别的合伙人名下的渠道经理，不能被设为合伙人。
  - 预览时显示该用户目前按快照属于哪个区域。如果他原本在别的合伙人区域里，设立后他本人的消费和他以后的客户都归新区域；他原来邀请的人仍按原快照归属。
- 合伙人邀请的客户，与代理邀请的待遇相同：
  - 绑定时记为「代理邀请」，所以能领代理来源的注册赠送。
  - 不触发普通用户邀请奖励。
- 合伙人本人不再拿任何代理分润和邀请奖励：`agent_direct`、`agent_diff`、`invite_percent`、`invite_fixed`。
  - 从设立那一刻起不再发放，这部分留在区域利润里，一起参与分成。
  - 已经发放的分润和分润余额不受影响，可以照常转余额，后台也可以照常登记提现。
- 合伙人名下的分销代理照常拿二级比例（7%）；原本给上级的差额（4%）留在区域利润里。
- 合伙人不能任命或取消任何代理。
- 分成比例可以改，从下一个自然月起生效。每张结算单记录当月使用的比例。

### 2. 区域与归属

- 后台把渠道经理挂到合伙人名下，挂上即永久，不能移出、不能改挂。
- 一个区域包括：
  - 合伙人自己的团队：直接邀请的客户、这些客户再邀请的人、合伙人名下的分销代理及其客户。
  - 挂靠的每个渠道经理的团队：渠道经理本人、他的客户、他名下的分销代理及其客户。
- 团队成员一律按现有绑定快照（归属代理、上级一级）判定，与团队消费页口径一致。
- 判定顺序：
  1. 本人是合伙人或已挂靠的渠道经理：归自己的合伙人（或所挂靠的合伙人）。
  2. 否则看绑定快照：先看归属代理，再看上级一级。第一个是合伙人或已挂靠渠道经理的，决定该用户归哪个区域。
  3. 都不是：不属于任何区域，利润全归平台。
- 只往后算，精确到时刻：
  - 计入起点 = 「合伙人设立 / 所属渠道经理挂靠」与「该用户绑定」两者中较晚的时刻。
  - 起点之前的消费不算。之后才注册的客户从注册那一刻算起。
  - 某人当上合伙人之前邀请的人，绑定快照里没有代理，不算进区域。75 号和 62 号都没有邀请过人，不受影响。
- 客户和代理的绑定规则不变。没有邀请人的用户，可以用现有的「补绑邀请人」划进区域。

### 3. 利润口径（每个区域、每个北京时间自然月）

区域利润 = 区域收入 − 区域上游成本 − 区域分润 − 区域专项支出 + 调整项

| 项 | 口径 |
|---|---|
| 区域收入 | 按财务页的收入确认规则，取区域用户在计入起点之后的部分：<br>- 付费余额按订单单位实收确认（已扣通道费、按退款冲减）<br>- 分润转入余额的消耗按 1:1 确认<br>- 赠送余额的消耗确认为 0<br>- 起点当天按「起点后消耗 ÷ 当天消耗」折算 |
| 区域上游成本 | 区域用户在起点之后的请求成本，公式与财务页一致；固定成本账号按 0 计 |
| 区域分润 | 来源用户是区域用户、在起点之后产生的分润流水（`agent_direct` / `agent_diff` / `invite_percent` / `invite_fixed`）；首充奖励、注册赠送按赠送余额处理，不计入这一项 |
| 区域专项支出 | 录入时指定了该区域的支出，按财务页摊销规则落在当月的部分 |
| 调整项 | 管理员加在结算单里的金额，可正可负，必须写说明 |

- 合伙人分成：
  - 当月利润 ≤ 0：分成 0，亏损累计到下个月。
  - 当月利润 > 0：先抵扣累计亏损，剩余部分 × 当月比例，结果四舍五入到分。
- 示例：分销代理的客户用掉 ¥100 付费余额，上游成本 ¥30。
  - 收入 96.80，成本 30，分润 11（分销代理 7、渠道经理 4）。
  - 区域利润 55.80，合伙人分成 22.32。

### 4. 结算单

- 每个合伙人每个自然月一张，从设立当月开始。
  - 已经结束、尚未确认的月份是草稿；当月是预估。两者每次打开都按最新数据重算，不需要定时任务。
- 状态流转：草稿 → 已确认 → 已付。
  - 已确认：金额冻结，之后数据再变也不改。这样做是因为用量明细 90 天后会被清理，成本重算也会改写历史数字。
  - 已付：记录打款日期和备注。
- 确认规则：
  - 必须按月份先后确认，因为累计亏损依赖上一张结算单。
  - 当月不能确认。
- 调整项只能加在未确认的月份上。已确认的月份发现差错，在之后月份的草稿里加调整项。
- 结算单内容：
  - 各项合计、累计亏损（期初 / 期末）、比例、分成。
  - 按渠道经理拆分，合伙人自己的团队单列一行。
  - 成本按分组、按模型拆分。
  - 调整项清单。
- 可以导出 CSV。

### 5. 页面

**合伙人端**：放在现有「邀请返利」区。
- 「邀请 / 团队消费」页签旁新增「利润分成」页签，只有合伙人能看到。
- 邀请页对合伙人显示合伙人身份和分成比例，不显示代理比例和任命按钮。
- **团队消费**：合伙人看到整个区域。
  - 汇总、趋势、模型占比。
  - 渠道经理列表，合伙人自己的团队单列一行。
  - 全区域客户列表。
  - 可以逐级点进：渠道经理 → 分销代理 → 客户 → 请求明细。
  - 隐私规则与代理端一致：邮箱脱敏；不显示余额、充值、IP、API Key、上游信息。
  - 这一页是经营信息，按现有成员展示，不受计入起点限制，范围仍为最近 90 天。
- **利润分成**：
  - 本月预估和累计亏损。
  - 历次结算单及明细。
  - 按渠道经理拆分的消费、收入、成本、分润、利润。
  - 成本按分组、按模型拆分。
  - 不出现账号名称、供应商、单价。

  - 合伙人列表：区域名、比例（含下月新比例）、挂靠数、本月预估、累计亏损、待确认月数。
  - 设为合伙人、挂靠渠道经理：先预览，再二次确认。
  - 修改区域名和比例。
  - 结算单：查看、调整项、确认、标记已付、导出。
- 代理列表：增加「所属合伙人」列和筛选；合伙人账号显示「合伙人」标识，不能改档位。
- 财务页：
  - 支出录入增加可选的「区域」字段。
  - 月度利润表增加「合伙人分成」和「平台净利润」两列。合伙人分成按整月计入：已确认的用确认金额，未确认的用草稿或预估，并标注「预估」。
  - 平台净利润 = 原利润 − 合伙人分成。

### 6. 权限

- 合伙人只能看自己的区域，只能点进挂在自己名下的渠道经理；非合伙人访问合伙人接口返回 403。
- 合伙人接口不返回账号名称或账号 ID、供应商、单价、客户完整邮箱。
- 设立合伙人、挂靠、修改比例、结算单相关操作仅限管理员，经现有审计中间件记录。
